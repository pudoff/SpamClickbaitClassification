## 2. Архитектурные решения (ADR)

### ADR-01. Источник аудио — голосовые, присланные боту

- **Контекст:** курс требует классифицировать аудиосообщения из Telegram; команда выбрала бота. Стороннее приложение не имеет доступа к чужим звонкам и мессенджерам (`02` §5.1).
- **Решение:** пользователь пересылает или записывает голосовое в личный чат с ботом. Группы и Telegram Business — этапы R2 и R3.
- **Последствия:** автоматической проверки всех входящих нет; сценарий полностью опирается на официальный Bot API.

### ADR-02. ASR + текстовый классификатор; baseline — модель 2 из `model.ipynb`

- **Решение:** GigaAM → `clean_text` → TF-IDF (word 1–2 + char_wb 3–5) + LR с калибровкой. Развитие — rubert-tiny2 (E-3). Гибрид — эксперимент E-4. Прямая аудиоклассификация отклонена.
- **Последствия:** готовая работа команды переиспользуется; качество зависит от ASR и от исправления смещения датасета (R-36).

### ADR-03. Обработка на сервере проекта, без облачных ASR

- **Решение:** ASR и классификатор — в `inference-api` на сервере, внешние сервисы распознавания не используются.
- **Последствия:** аудио не уходит третьим лицам; нагрузка ограничена ресурсами сервера.

### ADR-04. Синхронная обработка, long polling

- **Решение:** одно голосовое — один запрос к `inference-api` — один ответ. Обновления Telegram приходят через `getUpdates`.
- **Последствия:** не нужны публичный HTTPS и открытые порты; при простое обновления хранятся до 24 ч. Вебхук — этап R6.

### ADR-05. Два сервиса в Docker Compose; prod — сервер, dev — локально

- **Решение:** `bot` + `inference-api` (профиль `core`), MLflow + Label Studio (профиль `ml`). Один `compose.yaml` для сервера и локальной разработки, различаются только `.env`. Без Kafka, Airflow, Kubernetes и Prometheus.
- **Последствия:** любой участник поднимает полную копию у себя; одна точка отказа на сервере допустима для учебного проекта.

### ADR-06. Таксономия: три метки + отдельный статус

- **Решение:** `label` ∈ {`spam`, `clickbait`, `normal`}; `status` ∈ {`classified`, `uncertain`, `not_classified`}; `reason`. Соответствие меткам датасета: 0 → `normal`, 1 → `spam`, 2 → `clickbait`.
- **Последствия:** новый класс — MAJOR-версия API.

### ADR-07. Отказ от классификации никогда не равен `normal`

- **Решение:** низкая уверенность → `uncertain`; тишина, короткая речь, другой язык → `not_classified`; сбои → «⚠️ Ошибка проверки».

### ADR-08. Данные пользователей для обучения — только свои голосовые с явным согласием

- **Контекст:** команда разрешила использовать данные. Bot Platform Developer Terms п. 4.3 допускают это только для данных, переданных пользователем напрямую, при явном, активном и отзывном согласии. Content Licensing требует согласия всех причастных пользователей.
- **Решение:** `/consent` выключен по умолчанию. Сохраняются только собственные (не пересланные) голосовые и записи `/record`. Пересланные голосовые классифицируются, но не сохраняются. Telegram ID хранится в виде солёного хеша. Есть удаление и отзыв согласия. Фиксированных сроков нет — хранение до удаления, отзыва или закрытия проекта.
- **Последствия:** обучающих голосовых меньше, но использование соответствует условиям платформы.

### ADR-09. Выпуск модели — через ворота и согласие команды

- **Решение:** кандидат → ворота `05` §6 → проверка в локальном Docker → согласие ≥ 3 из 4 (R-ML и R-ASR обязательно) → `production` на сервере → 7 дней наблюдения → откат при необходимости.

### ADR-10. Раздельные версии API и моделей

- **Решение:** API — `/v1` + `info.version` (2.0.0); модели — `asr_model`, `lid_model`, `classifier_model`, `decision_policy` в каждом ответе.

### ADR-11. Без LLM в онлайн-контуре

- **Решение:** LLM допускается только офлайн для синтетических текстов с ручной проверкой.

### ADR-12. Без URL-входа

- **Решение:** бот скачивает файлы только через `getFile` с `api.telegram.org`; `inference-api` принимает только загруженный файл.

### ADR-13. Telegram-бот вместо мобильного приложения

- **Контекст:** версия 1.0 предлагала Android-приложение; курс требует бота.
- **Решение:** aiogram 3; мобильный клиент не разрабатывается.
- **Последствия:** нет работ по Android и iOS; все пользователи Telegram на любой платформе могут пользоваться ботом.

### ADR-14. Модуль ASR — GigaAM-v3 `v3_e2e_rnnt` + Silero VAD + LID faster-whisper `base`

- **Контекст:** готового модуля нет. Нужен русский ASR, локально, с открытой лицензией.
- **Альтернативы:** Whisper (faster-whisper), T-one, Vosk, облачные ASR.
- **Решение:** GigaAM-v3 (MIT; по данным авторов средний WER 11.2 % для e2e против 21.0 % у Whisper; в обучение входил домен голосовых сообщений). Silero VAD режет речь на сегменты ≤ 20 с (у `transcribe` лимит 25 с) — так не нужен pyannote с закрытой моделью. faster-whisper `base` используется только для определения языка.
- **Последствия:** три модели в сервисе; ≈ 3–4 ГБ RAM. Выбор подтверждается экспериментом E-1 на наших голосовых.

### 3.1. Календарный план до 12.12.2026

С 01.10 до 12.12 — 72 дня, около 10 недель. Критический путь: **сбор и разметка голосовых (D1) → эксперименты (M1) → валидация (V1)**. Поэтому сбор голосовых начинается уже на второй неделе, как только заработает `/record`.

| Недели | Даты | Этапы | Веха (к концу периода) |
|---|---|---|---|
| 1 | 01.10–04.10 | S0 | Роли распределены, документы приняты, боты созданы, сервер запрошен (Q-11) |
| 2–3 | 05.10–18.10 | D0, B0 | Отчёт D0 по групповому сплиту; бот с `/start`, `/consent`, `/record` и заглушкой классификатора работает в локальном Docker (T-DEP-01); **с 12.10 идёт сбор голосовых** |
| 3–4 | 12.10–25.10 | A1, D1 (начало) | Модуль ASR в `inference-api`; E-1 на первых 100 голосовых; собрано ≥ 300 голосовых |
| 5–6 | 26.10–08.11 | D1, M1 (начало) | **08.11: voice-holdout ≥ 400 и voice-calib ≥ 200 заморожены**; E-2 и E-2b на text-test |
| 7 | 09.11–15.11 | M1 | E-2a (TTS), E-5, калибровка; кандидат `classifier@1`, отчёт по воротам |
| 8 | 16.11–22.11 | P1 | Выпуск на сервер (если он есть, иначе в dev); T-PERF-01; бот доступен внешним пользователям |
| 9 | 23.11–29.11 | V1 | Пилот (≥ 10 пользователей), прогон `05` §9; **29.11 — заморозка функций** |
| 10 | 30.11–06.12 | V1, исправления | Исправлены дефекты пилота, финальные метрики; **06.12 — заморозка кода и модели** |
| 11 | 07.12–11.12 | Отчёт | Отчёт (в том числе E-2a), презентация, демо-видео, репетиция защиты |
| — | 12.12 | Сдача | Всё готово |

Правила, чтобы успеть:

- **Сокращение объёма при отставании больше недели** (сокращается сверху вниз):
  1. эксперименты E-3 и E-4;
  2. этапы R1–R6;
  3. `/stats` упрощается до выгрузки CSV;
  4. voice-holdout уменьшается до ≥ 300 (≥ 80 на класс) с записью в журнал решений.
- **Не сокращаются** — это требования кейса и минимальный продукт: бот с ASR и классификатором, TTS-эксперимент E-2a, статус «не проверено», удаление данных, отчёт метрик на реальных голосовых.
- Каждое воскресенье — 30-минутный созвон по таблице вех. Отставание на неделю запускает сокращение объёма.
- Если сервер не появится до 15.11, P1 и V1 проходят в dev-окружении одного участника. Для защиты этого достаточно: бот работает, пока запущен Docker.
