# Деплой и контейнеризация

Итоговая защита. Образцы подхода: практики В10 (стратегии деплоя) и В11 (Docker/Compose) курса.

## 1. Что реализовано сейчас (рабочий маршрут)

**Контейнеризация уже есть в проекте:**

- `inference-api/Dockerfile` — образ сервиса (Python 3.12, CPU-only PyTorch, зависимости
  из корневого `poetry.lock`); код копируется в образ, модели — нет (том `models/`);
- `compose.yaml` — сервис `inference-api` (порт из `.env`, healthcheck по `/healthcheck`,
  `restart: unless-stopped`) + `trainer` в профиле `train` (воспроизводимое обучение LR);
- `.env.example` — шаблон настроек: `API_PORT`, `MODEL_FILE`, `TAU`, `TAU_SPAM`;
- модели передаются комплектом (`manifest.json` + SHA-256 компонентов), не входят в Git/образ.

**Маршрут запуска (проверен командой, описан в корневом README):**

```bash
git clone … && git lfs pull          # df.csv ~380 МБ нужен только тренеру
cp .env.example .env
# получить комплект ансамбля у команды ИЛИ экспортировать:
docker compose --profile train run --rm trainer python -m training.export_ensemble …
docker compose up -d --build inference-api
docker compose ps                    # Up (healthy)
# Swagger: http://localhost:8000/docs
```

Без комплекта сервис стартует, но `/predict` и `/healthcheck` отвечают **503** с причиной —
молчаливой подмены модели нет. Запасной режим: отдельная LR (`MODEL_FILE=model.joblib`,
обучение тренером ~15 мин на всём df.csv или ~1 мин на 20 тыс. строк).

**Проверки в контейнере:** `pytest -q` (82 passed, 2 skipped без эталона Reports;
84 passed с примонтированным репозиторием), `ruff check`, `ruff format --check`.

## 2. Стратегия выпуска и отката

Текущий уровень зрелости — **ручной воспроизводимый выпуск** (MLOps-профиль, уровень 1):

1. Кандидат обучается в контейнере `trainer` (фиксированные конфиги, seed, версии).
2. Ворота качества (`TEST_PLAN.md` §3) + тесты в локальном Docker.
3. Согласование команды (≥3 из 4, обязательно R-ML и R-ASR).
4. Выпуск: комплект кладётся в `models/`, версия фиксируется в `.env`/манифесте,
   `docker compose up -d --force-recreate inference-api`; при старте проверяются
   SHA-256 и версия sklearn.
5. Наблюдение 7 дней (`MONITORING.md`).
6. **Откат ≤ 10 мин**: вернуть прежний комплект/тег образа и пересоздать контейнер.
   Поводы: ошибки > 5% проверок за сутки, coverage < 0.6, подтверждённая разметкой деградация.

Стратегия — **recreate с проверкой здоровья** (аналог blue-green на одном сервере:
старый комплект сохраняется рядом, переключение — смена пути в `.env`). Rolling/canary
не применяются: одна реплика, состояние только в артефактах.

## 3. Целевой prod-контур (концепт v2)

- Сервер проекта (16 ГБ RAM), Docker Compose, профили `core` (bot + inference-api)
  и `ml` (MLflow + Label Studio по требованию);
- образы с тегом git SHA; `docker compose pull && up -d`; откат — предыдущий тег;
- секреты (токен бота, соль, X-API-Key) только в `.env` (права 600), не в Git;
- наружу открыт только SSH; бот работает через long polling (входящие порты не нужны);
  Swagger/MLflow/Label Studio — через SSH-туннель;
- данные и модели на зашифрованном томе, ежедневный бэкап; DVC — версии данных,
  MLflow-реестр — версии моделей (алиасы candidate/production/previous);
- CI (GitHub Actions по решению владельца): ruff → pytest → валидация OpenAPI → сборка образов.

## 4. Честный учебный маршрут запуска (что демонстрируется на защите)

Полноценный prod с ботом и ASR **не развёрнут** — это осознанные границы учебного проекта.
Демонстрация решения возможна тремя способами без облака и платных сервисов:

| Способ | Что нужно | Что показывает |
|---|---|---|
| **Colab-ноутбук** `FinalProject/notebooks/demo_solution.ipynb` | только браузер + `demo_sample.csv` (9.5 МБ) | данные → валидация → 3 эксперимента + ансамбль (MLflow) → политика отказа → дрейф → FastAPI через TestClient |
| **Локальный venv** | Python 3.11+, `venv` проекта | те же эксперименты на 60 тыс. строк (`run_experiments.py`), 11 тестов демо, MLflow UI |
| **Docker-сервис** | Docker Desktop + комплект ансамбля | боевой `/predict` на полном ансамбле, Swagger, healthcheck, 84 теста в контейнере |

Первый способ — минимальный работающий сценарий «из коробки»; в реальном проекте его
место занял бы CI-пайплайн: те же шаги (валидация → обучение → тесты → ворота → образ →
деплой) автоматизированы, а ноутбук остаётся исследовательским инструментом.

## 5. Риски деплоя и меры

| Риск | Мера |
|---|---|
| Неполный/несовместимый комплект модели | манифест + SHA-256 + проверка версии sklearn; 503 вместо тихой деградации |
| Разная нормализация обучения и инференса | версия нормализатора в мете/манифесте; неизвестная версия → 503 |
| Дрейф входных данных после выпуска | PSI/coverage-мониторинг, аллерты (`MONITORING.md`), откат |
| Утечка секретов | `.env` вне Git, `.dockerignore`, логи без текста и идентификаторов |
| Рост нагрузки (ASR на CPU) | очередь в боте (2 параллельных запроса), лимиты, таймауты, 503 + Retry-After |
