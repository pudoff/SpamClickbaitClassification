# План мониторинга

Итоговая защита. Образцы: практики В12 (мониторинг в продакшене) и В13 (дрейф) курса;
проектные решения — концепт v2 `03` §10, `05` §4. Для одного сервера с учебной нагрузкой
Prometheus/Grafana избыточны (ADR-05): MVP — структурированные JSON-логи, `/stats` бота
и еженедельный отчёт; при росте нагрузки те же метрики выгружаются в Prometheus.

## 1. Технические метрики

| Метрика | Источник | Норма / цель |
|---|---|---|
| Доступность `/healthcheck` (доля 200) | Docker healthcheck, опрос раз в 30 с | 100%; 503 = модель не загружена |
| Латентность `/predict` p50/p95 | middleware-логи (`latency_ms`, как в демо-ноутбуке) | p95 ≤ 50 мс (текст); целевой конвейер с ASR: p95 ≤ 15 с на голосовое ≤ 60 с |
| Доля ошибок 5xx / 422 | JSON-логи по `request_id` | 5xx < 1%; всплеск 422 — сигнал о смене формата входа |
| Очередь бота и время ожидания | `check.timings_ms` в SQLite | ожидание p95 ≤ 2 с; очередь > 2 — предупреждение пользователю |
| Ресурсы контейнера (CPU/RAM) | `docker stats` / cAdvisor при росте | RAM < 4 ГБ (текстовый сервис), запас до 16 ГБ сервера |
| Рестарты контейнера | `restart: unless-stopped` + счётчик рестартов | > 3 рестартов/час — расследование |

В логах **нет текста сообщений, аудио и Telegram ID** — только псевдонимы, `request_id`,
статусы, время и версии моделей (приватность, концепт v2 §8).

## 2. Метрики данных и модели

| Метрика | Как считается | Зачем |
|---|---|---|
| **PSI распределения длины текста** (слова) | эталон — fit-выборка обучения; окно — сутки/неделя; бины по квантилям эталона | дрейф входа; в эксперименте E-DRIFT PSI=9.62 надёжно поймал сдвиг «короткие реплики» |
| PSI распределения предсказанных классов | логи `label` против test-распределения манифеста | сдвиг потока (например, волна спама) |
| **Coverage** (доля `classified`) | логи `status` | рост отказов = модель «не узнаёт» вход |
| Доля `uncertain` и средняя confidence | логи | деградация уверенности раньше, чем видна по отзывам |
| Доля `not_classified` по причинам (no_speech, unsupported_language…) | логи ASR-конвейера (целевая версия) | дрейф языка/качества аудио |
| Доля отзывов «👎 Неверно» | SQLite `feedback` | прокси-качество без разметки |
| **Macro-F1, P/R по классам, FPR normal→spam** на свежей разметке | еженедельная партия ≥ 50 записей `/record` + размеченные отзывы (Label Studio, двойная разметка) | истинное качество; дрейф сам по себе падения не доказывает |
| ECE (калибровка) | размеченная выборка, 10 бинов | уверенность ≠ правильность; цель ≤ 0.08 |
| WER/CER ASR | эталонные расшифровки ≥ 150 | качество распознавания отдельно от классификатора |

Разделение понятий (концепт v2 §4): confidence — выход модели; калибровка — согласие
confidence с частотой правильных ответов; дрейф — изменение входов; качество — метрики
на свежей эталонной разметке. **Дрейф запускает разметку и анализ, а не автопереобучение.**

## 3. Аллерты (≥3) и действия при отклонениях

| ID | Условие (порог) | Severity | Действия |
|---|---|---|---|
| **A-1** | `/healthcheck` ≠ 200 дольше 5 мин ИЛИ > 3 рестартов контейнера/час ИЛИ 5xx > 5% запросов за час | critical | Дежурный смотрит `docker compose logs`; проверка комплекта (SHA-256, версия sklearn); откат на предыдущий комплект/тег образа (≤ 10 мин); пользователям — «⚠️ Ошибка проверки», никогда не «Обычное» |
| **A-2** | Coverage < 0.60 за сутки (норма ≈ 0.90) ИЛИ доля `uncertain` выросла > 1.5× к базовой неделе | warning | Выгрузить примеры отказов; проверить PSI длины и классов; запустить внеочередную разметку ≥ 50 записей; при подтверждённой деградации — переобучение кандидата через ворота качества |
| **A-3** | PSI длины текста > 0.25 за неделю (умеренный 0.1–0.25 — наблюдение) ИЛИ macro-F1 на свежей разметке < 0.75 ИЛИ F1 кликбейта упал > 5 п.п. к прошлой партии | warning → critical при подтверждении | Дрейф-расследование: срезы по длине/классу; доразметка коротких реплик; кандидат на переобучение (BPMN `bpmn_retrain.bpmn`); выпуск только через ворота и согласование ≥3 из 4 |
| **A-4** | p95 латентности > 15 с (целевой конвейер) или > 200 мс (текстовый) за 15 мин ИЛИ очередь бота > 10 | warning | Проверить CPU/RAM, `TORCH_NUM_THREADS`; деградация: лимиты и 503 + Retry-After; при систематическом превышении — оптимизация (ONNX, E-1b) или масштабирование |
| **A-5** | Доля «👎 Неверно» > 10% за неделю ИЛИ precision spam < 0.85 на свежей разметке | warning | Разбор ошибок с двойной разметкой; проверка FPR normal→spam (цель ≤ 5%); пересмотр порогов τ/τ_spam на калибровочной выборке (E-5), не «на глаз» |

Каждый аллерт имеет владельца (R-ML — модельные, R-BOT/R-ASR — технические), канал
(сообщение в чат команды дежурному) и запись в журнал решений. Ложные срабатывания
разбираются еженедельно; пороги пересматриваются один раз после первого voice-baseline
с записью в журнал (правило концепта v2).

## 4. Дашборд (эскиз, по образцу В12)

Панели: здоровье сервиса (uptime, 5xx, p50/p95) · поток проверок и доли статусов
(classified/uncertain/not_classified по причинам) · распределение меток и средняя
confidence · PSI длины и классов (текущее окно против эталона) · отзывы «👎» и
macro-F1 последних партий разметки · версии моделей в ответах (`model_version`).

## 5. Что реализовано сейчас

- JSON-логирование сервиса (`app/logs.py`), версии моделей в каждом ответе;
- healthcheck в Docker Compose;
- демо middleware с `request_id`/латентностью/статусом без текста — ноутбук, раздел 6;
- PSI/KS-инструменты (`FinalProject/demo/drift.py`) и подтверждённый дрейф-сценарий E-DRIFT;
- `/stats`, сбор отзывов и еженедельная разметка — план развития существующего демо-бота.
